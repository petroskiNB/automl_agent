## 2. Что именно мы создаём

Это программа AutoML общего назначения: по `task.md` и CSV она исследует задачу,
обучает табличные модели, проверяет качество и формирует `submission.csv`.
Один entry point обслуживает регрессию и классификацию; отдельные стратегии
включаются по типу задачи, метрике, временной структуре и схеме данных.

Qwen работает удалённо через API. Его веса не скачиваются на ПК и не дообучаются
на наших CSV. Qwen выбирает гипотезы, параметры и инструменты. Модели CatBoost,
XGBoost, LightGBM и нейросети обучаются на ПК либо внутри контейнера платформы.

Упрощённый цикл:

`task.md + CSV → Python-контроллер → Qwen → инструмент обучения/анализа → метрики → Qwen → выбор pipeline → экспорт`

Память агента — это сохранённые рецепты, метрики, журналы и их сокращённые снимки,
которые контроллер передаёт Qwen. Это не изменение весов Qwen и не автоматическая
память API обо всех прежних запусках.

Текущая основная реализация находится в `champion_solution/`. Корневые старые
`solution.py` и `neural_solution/` относятся к более ранним линиям разработки.

## 3. Среда, ограничения и упаковка

Принятые для разработки ограничения: Python 3.12, 8 CPU, 32 ГБ RAM, без GPU,
до трёх часов на задачу. В основных командах используется бюджет 9900 секунд
на задачу с резервом 1800 секунд на завершение и экспорт. Ожидание API и обучения
входит в общий бюджет. Лимит одного инструмента и бюджет AutoML — отдельные ограничения.

Текущий типичный запуск: один исследователь, один training job, 8 CPU-потоков,
reviewer включён, analyst выключен. Реализована возможность 1–3 исследовательских
ветвей и до двух одновременных обучений, но большее число агентов не доказало
самостоятельного прироста качества. Общий CPU-бюджет делится между обучениями.
Число участников внутреннего ансамбля TabM (`ensemble_size`) не равно числу агентов
Qwen и не равно числу CPU-потоков.

Ключи API задаются переменными окружения. В отчёт, исходники и ZIP ключи не включаются.
Основная LLM в выполненных пользовательских запусках: `qwen/qwen3.8-27b`.

Платформа переносит **только корневые `.py` и `requirements.txt`**. Это критичное
ограничение: ранняя версия требовала `reference_recipes.json` и получила ноль из-за
FileNotFoundError ещё до обучения и API. Рецепты перенесены в `reference_recipes.py`.
JSON с состоянием, создаваемые уже во время работы, допустимы.

Архивы содержат код и зависимости; обученные локальные модели, история, CSV и ключи
в них не упаковываются. Поэтому платформа каждый раз начинает новое исследование.
Она не получает автоматически нашего локального победителя и его обученные веса.
В частности, восстановленный локальный CSV не заменяет ZIP агента для платформы.

Основные версии: CatBoost 1.2.8, LightGBM 4.6.0, XGBoost 2.1.4, sklearn 1.5.2,
PyTorch 2.5.1, AutoGluon 1.3.1, FLAML 2.3.6, LightAutoML 0.4.2.
TabM 0.0.3 и numerical embeddings 0.0.12 включены как Python-исходники с лицензиями;
загрузка предобученных весов не требуется. Полный список — `champion_solution/requirements.txt`.

## 4. Основные этапы разработки

1. Проверили API и создали цикл Qwen → исполнение Python → возврат результата.
   На первых запусках агент ошибался в параметрах CatBoost и типах категорий,
   получал traceback и исправлял код.
2. Добавили ограничения времени, изоляцию рабочих каталогов, сохранение рецептов,
   историю экспериментов, продолжение через `--resume`, контроль данных и кода по SHA-256.
3. Расширили семейства: CatBoost → LightGBM/XGBoost → MLP/residual MLP. Совместили
   основную и нейросетевую линии; успешный архив друга оказался гибридным агентом,
   а не решением исключительно на нейросетях.
4. Добавили reviewer/analyst, анализ ошибок и независимые исследовательские ветви.
   Выяснили, что советы LLM нужно проверять: роли иногда смешивали разные метрики,
   неверно описывали исполнение либо завершали работу без всех этапов.
5. Заменили опору на один holdout более строгими OOF/временными проверками,
   внутренней калибровкой решений, временной историей и ансамблями.
6. Исправили платформенную упаковку без внешнего JSON, маршрутизацию задач,
   выбор и экспорт проверенного pipeline, сохранение контрольных ZIP.
7. Подключили отдельные инструменты AutoGluon, FLAML и LightAutoML с бюджетами,
   общими фолдами, сохранением моделей и собственными протоколами экспорта.
8. Добавили три регрессионных anchors и их фиксированный ансамбль. Эта линия v7
   дала лучший подтверждённый платформенный результат 2284.823.
9. В v9 одновременно расширили AutoGluon, добавили настоящий TabM, OVR-экспертов,
   fuzzy-историю зданий и эксперта высокого потребления. Платформенный результат
   316.66 показал, что такой широкий переход нельзя считать подтверждённым улучшением.
10. После v9 восстановили потерянные AutoGluon-отчёты без обучения, перепроверили
    XGBoost на исходных фолдах и доработали TabM для следующего контролируемого опыта.

## 6. Регрессия: энергопотребление зданий

Известный локальный набор: target `site_eui`, 53 308 train-строк и 22 449 test-строк.
Метрика — RMSE, меньше лучше. Train содержит годы 1–5, test — год 6.
Набор похож на WiDS Datathon 2022; это идентификация по схеме, не основание
использовать внешние метки или готовые предсказания.

Исторический лучший single-holdout RMSE был около **38.5966**. Это оценка на одном
проверочном году после большого числа адаптивных экспериментов, а не независимый тест.

Текущая схема проверки: внешние годы **3, 4, 5**, обучение каждого фолда только
на более ранних годах. Early stopping/подбор — внутри прошлого, без внешних меток.
Сравнение: mean RMSE, затем latest, затем worst при равенстве. Ранее уже изученные
годы считаются development validation; наличие нескольких фолдов не устраняет
адаптивное переобучение на самой схеме проверки.

Реализовано:

- Исторические target-агрегаты по ключам зданий и группам: количество, среднее,
  последнее значение, давность и разброс. Даже для обучающих строк исключаются
  одновременные и будущие наблюдения.
- Иерархия широких ключей, сглаживание, backoff к группам и округление площади.
  Широкое совпадение — гипотеза о похожем объекте, не доказанный building_id.
- Остаточная модель относительно причинного исторического baseline. Строки без
  допустимой истории исключаются из обучения остатка; baseline возвращается до clipping.
- Неотрицательный clipping включён в сохранённый pipeline и применяется одинаково
  при валидации и экспорте; CSV вручную не исправляется.
- Фиксированные ансамбли 2–4 разных temporal pipelines; проверка одинаковых строк,
  запрет вложенных ансамблей и двойного учёта reference-алиаса.
- Три anchors: CatBoost с иерархией, CatBoost с точным ключом без ELEVATION,
  LightGBM с иерархией. Они заново измеряются на данных запуска.

| Сопоставимый локальный кандидат | Mean RMSE | Последний год | Худший год |
|---|---:|---:|---:|
| **Фиксированный ансамбль трёх anchors** | **39.9274** | **36.3092** | **50.4972** |
| CatBoost с иерархической историей | 40.7018 | 34.5123 | 52.3780 |
| CatBoost с точным ключом | 40.9189 | 35.0682 | 52.6382 |
| LightGBM с иерархией | 42.3302 | 45.4527 | 49.2640 |

Разные модели сильны в разные годы: победитель последнего года не обязательно
победитель среднего. Средний RMSE 39.9274 нельзя сравнивать как ухудшение с 38.5966
на одном другом holdout.

FLAML: отдельный bounded search на внутреннем прошлом, точный refit выбранного
рецепта, общий temporal рейтинг/ансамбль/экспорт. В измеренном опыте standalone mean
около **42.2004**, источник **40.7018**, смесь 50/50 **40.5296**. Это хуже общего
ансамбля **39.9274**, но не доказывает бесполезность FLAML на скрытых задачах.

Первый LightAutoML: linear_l2/LGB/CB, standalone mean **42.9750**, смесь с источником
**40.7270**. Затем добавлены исходные строковые категории, ограниченные tuned-варианты
и full-past refit. Их Qwen-прогоны прерывались на API до запуска LightAutoML, поэтому
результат этих новых режимов пока не подтверждён.

Новые регрессионные инструменты v9: сопоставление близкой площади внутри устойчивых
групп и эксперт высокого потребления с gate-классификатором. Порог высокого target
определяется на train; на inference gate использует только признаки и прошлую историю.
Есть четыре режима reference/fuzzy_history/tail_expert/tail_fuzzy. Сам код и экспорт
проверены; подтверждённого реального прироста этого направления пока нет.

## 7. Классификация: сетевой трафик

Известный набор: target `attack_cat`, 10 классов, 87 670 train-строк и 41 166 test-строк,
42 признака. Метрика Macro F1, больше лучше. Схема похожа на UNSW-NB15; не использовались
внешние метки. Непропорционально важны редкие классы, поскольку Macro F1 даёт всем
классам одинаковый вес.

Ранний frozen holdout: 70 136 train / 17 534 validation. Исторический XGBoost recipe49
получил **0.6651474**; в последнем extended-run он повторился как exp5. Сам по себе
этот holdout не является доказательством устойчивого выигрыша.

Усиленная проверка: три одинаковых внешних стратифицированных фолда; внутри outer
train выделяется calibration; preprocessing, early stopping и правила решения не
используют внешние метки. Сохраняются OOF-вероятности и модели каждого фолда.
Веса ансамбля и множители классов настраиваются только на внутренней калибровке.
Экспорт классификации обычно усредняет сохранённые fold-модели; это не автоматическое
новое обучение на всём train.

### Фактические результаты последнего завершённого extended-run

| Кандидат | Mean Macro F1 | Worst | Pooled OOF F1 |
|---|---:|---:|---:|
| Исходный OOF + macro decision | 0.6296683 | 0.6204287 | 0.6284641 |
| OVR-эксперты + macro decision, первоначально экспортированы | 0.6297994 | 0.6199530 | 0.6286859 |
| AutoGluon boosting + macro decision, восстановлен | 0.6312730 | 0.6241307 | 0.6312216 |
| **AutoGluon diverse + macro decision, восстановлен** | **0.6328643** | **0.6289046** | **0.6325865** |

Standalone AutoGluon был слабее: boosting около **0.59389**, diverse **0.59869**.
Выигрыш получен у комбинации с reference и правилом решения; это не доказательство,
что каждая добавленная модель сильнее бустинга или что вся прибавка обусловлена сетью.
В части фолдов калибровка вообще выбирала нулевой вес AutoGluon.

OVR Backdoor/Analysis/DoS дал среднюю прибавку всего **0.0001311**, при ухудшении
худшего фолда. Убедительного прироста здесь пока нет; расширять его бюджет первым
приоритетом нецелесообразно.

### TabM

Подключена авторская архитектура TabM с внутренним параметрически эффективным
ансамблем. Обучение минимизирует средний loss отдельных участников, не loss
усреднённого прогноза. При классификации усредняются вероятности, не logits.
Macro F1 используется для оценки/early stopping; это не прямой дифференцируемый F1-loss.

Первая CPU-конфигурация: width128, 2 блока, k8, до 40 эпох, batch512, AdamW,
learning_rate0.002, weight_decay0.0003. На одном holdout:

- без numerical embeddings: **0.5656804**;
- с PLE: **0.5723010**;
- PLE на трёх внешних фолдах: mean около **0.5500741**.

Обе эти сети обучались без весов классов, тогда как сильные бустинги использовали
SqrtBalanced. Поэтому это не полное сравнение возможностей архитектур.
В новом коде добавлен `numeric_preprocessing=quantile`, fit строго на train;
убраны постоянные missing-индикаторы. Старый robust-режим сохранён совместимым.
Следующая парная гипотеза — PLE/quantile без весов против SqrtBalanced с одинаковыми
признаками/seed. Её законченного результата на реальных данных пока нет.

### Свежая перепроверка XGBoost

Старый OOF использовал рецепты `[1,2,4]`; лучший на holdout exp5 был найден позже
и туда не попал. Его спецификацию перенесли в новый запуск, сохранив точные внешние
и внутренние индексы, но не импортируя старые модели/score в новый реестр.

Свежая оценка exp5: **mean 0.6128243**, **worst 0.5967548**, **pooled OOF 0.6118070**.
Это ниже прежнего raw XGBoost exp2 mean **0.6196254** и лучшего восстановленного
ансамбля. Исторический single-holdout-рекорд не подтвердил преимущество на OOF.

### Диагностика данных

Adversarial validation дала AUC около **0.815**: train/test заметно различимы по
признакам. Из одного AUC нельзя сделать вывод, что сдвиг «некритичен», или доказать
изменение распределения target при фиксированных признаках. Test-like срез используется
для диагностики, а не для подбора весов или автоматической смены победителя.

Ранее обнаружены **14 829 train-строк** в группах с одинаковыми 42 признаками,
но разными метками; особенно много таких строк среди Analysis/Backdoor/DoS.
Это ограничивает возможность различать часть объектов только по данным признакам,
но не устанавливает точный максимально достижимый Macro F1.

## 8. Что случилось с локальным AutoGluon и что восстановлено

В пользовательском локальном запуске `--step-timeout=1800` совпадал с бюджетом
каждого AutoGluon suite `time_limit=1800`. Два профиля шли последовательно и были
остановлены внешним контроллером ровно на 1800 секундах каждый. Это не API timeout.

Однако уже были сохранены модели, предсказания и scores всех трёх внешних фолдов.
Не успел сохраниться общий report, поэтому финальный selector не увидел кандидатов.
Qwen ошибочно описал ситуацию как незавершённое обучение и параллельный запуск.

Сделано восстановление в отдельном каталоге с точным исходным runtime из v9 ZIP:
проверены identity, данные, внешние/calibration-разбиения, классы, алгебра сохранённых
правил смешивания, метрики и файлы native-моделей. Проверены SHA256 204 артефактов
boosting и 288 diverse. В audit указано `training_performed=false`.

Лучший pipeline заново экспортировал **41 166** прогнозов без обучения. Исходный
run и ZIP сохранены. Большие native-model `.pkl` в восстановленной копии связаны
hard links для экономии около 6 ГБ: этот каталог предназначен для чтения/экспорта,
не следует вызывать там fit/save predictor.

В рабочем коде после v9 исправлены:

- резерв времени на агрегацию/запись отчёта, ускоренная агрегация через числовые метки;
- перевод wall-clock deadline в monotonic, вместо смешивания двух шкал времени;
- запас внешнего watchdog при сохранении общего дедлайна и резерва экспорта;
- использование полностью завершённых fold-checkpoints и восстановление перед выбором;
- статус timed_out вместо зависшего running; потраченный бюджет не возвращается;
- завершение с корректно опубликованным OOF даже при отсутствии single-holdout best;
- импорт проверенных планов фолдов и отдельная перепроверка исторических спецификаций.

## 9. Что означает падение v9 до 316.66

### Подтверждено

На скриншоте указан v9, балл 316.66, статус «Успешно» и длительность 11597.0 сек.
По сравнению с v7: 2284.823 → 316.66, минус 1968.163 балла, около 86.14%.

v7 и v9 используют CPU8 и общий бюджет9900. В v7 FLAML регрессии имел1800 сек;
в v9 он отключён. LightAutoML в обеих сборках выключен. В v9 включён extended-plan,
добавлены новые обязательные направления, steps60→80, увеличены ожидание и повторы API.

**В архиве v9 лимит шага — 3600, а не локальные 1800.** Там всё ещё были старые
ограничения AutoML-wrapper и отсутствие восстановления отчётов, но конкретный
локальный обрыв на1800 нельзя напрямую объявить причиной платформенного316.66.

Последние изменения quantile-TabM, frozen-fold recheck и recovery внесены после
сборки v9; этот низкий скор их не оценивает.

Статус «Успешно» не показывает качество и не доказывает выполнение всех этапов.
Программа может корректно завершиться с более слабым fallback после внутренних
ошибок. Из отображаемого общего времени нельзя восстановить время каждой задачи,
очередь и причину остановки; число11597 само по себе не доказывает нарушение лимита
одного model fit или отдельной задачи.

### Основные гипотезы — пока НЕ диагноз

1. Новая траектория поиска и конкуренция за время оставили более сильные кандидаты
   незавершёнными, без общего отчёта или невыбранными. Локально такой механизм уже
   воспроизведён. На платформе его нужно подтвердить отдельно.
2. Новые решения обобщились хуже на скрытых данных. TabM без весов оказался слаб,
   OVR дал почти нулевую прибавку, а множество адаптивных проверок не защищает от
   переобучения на development folds. Конкретный выбранный pipeline неизвестен.
3. Регрессия ухудшилась из-за изменения состава поиска: отсутствие FLAML, новые
   fuzzy/tail/нейросетевые кандидаты и ограниченный бюджет. Отключение FLAML —
   реальная перемена, но нет доказательства, что именно она объясняет всё падение.
4. API, скорость CPU/диска или память контейнера изменили число завершённых опытов.
   Более длинные повторы API также расходуют общий бюджет.
5. Возможна проблема выбора/экспорта, но доказательств перепутанных ID/меток или
   прежней ошибки JSON нет. В v9 есть структурная проверка CSV; она не проверяет
   качество скрытого test и не исключает все логические ошибки.

Без логов нельзя утверждать «виноваты нейросети», «виновато отключение FLAML» или
«нужно просто больше времени». Локальная смесь с diverse действительно лучше
прежнего локального экспорта; гипотеза «все новые модели плохие» тоже не подтверждена.

### Какие сведения нужны из платформенных логов

1. Результат/метрика/вклад каждой задачи отдельно и её exit status.
2. Фактические аргументы, бюджеты и затраты времени по этапам.
3. Последние ошибки API, worker timeouts, OOM/kill, незавершённые этапы.
4. `run_summary`, `research_progress`, `final_selection`, `final_output` обеих задач.
5. Классификация: какие рецепты вошли в OOF; завершились ли AG-профили; сохранились
   ли отчёты; какой pipeline фактически экспортирован вместо возможного fallback.
6. Регрессия: завершены ли три anchors; какой suite/mode победил; были ли применены
   новые специалисты/TabM; какие mean/latest/worst получены перед экспортом.

## 10. Что проверено и что ещё не проверено

Выполнены точечные проверки параметров, train-only preprocessing, взвешенного
per-member loss TabM, сериализации/reload, точных фолдов, восстановления сохранённых
AG-артефактов, отказа при испорченных данных, экспорта без обучения. Для последних
доработок отдельно прошли 7 AG mock-checks, 3 TabM F1, 3 frozen-recheck и 3 contracts.
Это разные короткие проверки, не единый полный прогон всех тестов проекта.

Проверялись компиляция и реальный entry point на двух маленьких задачах после
фильтрации файлов как на платформе, с подменённым API. Это проверяет доставку и
старт, не точность моделей на скрытых данных.

Реально выполнены восстановление/экспорт AutoGluon без fit и новая OOF-проверка
XGBoost exp5. Новая weighted/quantile TabM-пара ещё не имеет законченного подтверждённого
результата на реальных данных; последние рабочие изменения пока не получили
отдельного платформенного скора. Ранние синтетические нейросетевые цифры друга
не следует подменять ими метрики задач хакатона.

## 12. Как продолжать работу

Первый приоритет — разобрать v9 по отдельным задачам. До логов сохранять v7 как
известный лучший архив; не объявлять новый подход лучше только по объёму кода.
Следующий платформенный эксперимент делать с одной контролируемой переменой:
например, сильная baseline-линия плюс исправленное сохранение AutoGluon, без
одновременной замены регрессии, нейросети, порогов и распределения бюджетов.

Локально: завершить pair TabM PLE/quantile без весов и SqrtBalanced, сравнить на
точных исходных фолдах с raw XGBoost и сохранённым контролем. Затем проверить
независимость ошибок и ансамбль. OVR/новые агенты сейчас имеют меньший приоритет,
чем корректный сильный reference, завершённые отчёты и воспроизводимый экспорт.

Команда для подготовленного followup, если исходники не менялись и нет другого
живого процесса в этой папке (API уже задан в этом терминале):

```powershell
.\.venv_autogluon\Scripts\python.exe champion_solution/solution_torch.py tasks/classification/task.md `
  --output-dir outputs/champion_classification_followup_v2 `
  --resume outputs/champion_classification_followup_v2/agent_runs/followup_20261026 `
  --extended-research --threads 8 --researchers 1 --training-jobs 1 `
  --reviewer --no-analyst --autogluon-budget 3600 --flaml-budget 0 --lightautoml-budget 0 `
  --time-budget 9900 --max-steps 80 --step-timeout 3600 `
  --api-timeout 180 --api-retries 4 --instructions classification_followup_plan.md
```

Не запускать эту команду поверх уже работающего процесса. Не удалять lock вслепую.
На другом ПК `.venv` не переносится: нужно своё окружение и данные. Для нового
эксперимента использовать отдельный output-dir; старые модели не превращать в новые
метрики отключением fingerprint-проверок. В Git не отправлять ключи, данные,
venv, checkpoints и многогигабайтные AG-каталоги. Этот отчёт можно передать отдельно.
