# Агент AutoML: управляемые эксперименты

Проект для трека AutoML Альфа-Хака. Qwen через API выбирает эксперименты;
CatBoost/LightGBM обучаются локально, а при проверке — на платформе организаторов.
Qwen не дообучается. Ключ общий для команды, запросы расходуют общий бюджет.

## Быстрый старт для команды

1. Склонируйте репозиторий через `git clone <URL_репозитория>` и откройте его папку
   в терминале. URL возьмите в вашем Git-хостинге.
2. Установите Python **3.12**. На Windows можно выполнить
   `winget install --exact --id Python.Python.3.12`, затем открыть новое окно PowerShell.
   Проверка: `py -3.12 --version`.
3. Создайте окружение и установите зависимости по разделу ниже. Для обоих
   алгоритмов установите также LightGBM.
4. Скачайте данные у организаторов и разложите их по структуре ниже. Данных
   и логов в Git нет — каждый участник скачивает их отдельно.
5. Выполните проверки `--check` и тесты, затем проверьте API через `check_api.py`.
6. Задайте переменные подключения и запускайте задачи по одной.

```text
automl_agent/
├── solution.py              # Контроллер и API-цикл
├── research.py              # Обучение, метрики и выбор лучшей модели
├── check_api.py             # Один короткий запрос для проверки подключения
├── build_submission.py      # Сборка ZIP по явному списку файлов
├── requirements.txt         # Исходный список организаторов для платформы
├── test_solution.py
├── test_research.py
└── tasks/                   # Локальная папка, не отправляется в Git
    ├── regression/
    │   ├── task.md
    │   ├── train.csv
    │   ├── test.csv
    │   ├── data_dictionary.csv
    │   └── sample_submission.csv
    └── classification/      # Такой же набор из пяти файлов
```

`solution.py` управляет Qwen и временем. `research.py` выполняет обучение,
расчёт метрик и сохранение лучшего результата. MCP не требуется.

Инструменты агента:
- `inspect_data`: структура, пропуски и словарь данных;
- `configure_task`: цель, метрика и неизменное разбиение на весь запуск;
- `train_model`: эксперимент CatBoost или LightGBM, метрика, сохранение победителя;
- `run_python`: дополнительный анализ с генерацией кода.

Оценка и сохранение встроены в train_model: отдельного агента для этого нет.
Поддерживаются задачи с одним таргетом и метрики RMSE, MAE, Macro F1, Accuracy.
Вероятностные метрики, многомерный выход и другие виды задач пока не реализованы.
Схему валидации выбирает Qwen; контроллер фиксирует индексы и проверяет базовые
условия, но не может гарантировать предметную корректность выбранного разбиения.
Для временного разбиения колонка должна сортироваться хронологически (числовой
период или ISO-дата); произвольные строки дат пока автоматически не преобразуются.

## Подготовка

Установите Python 3.12. В PowerShell из корня проекта:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install openai==1.68.2 numpy==1.26.4 pandas==2.2.3 scikit-learn==1.5.2 catboost==1.2.8
```

Это минимальная локальная установка. Исходный `requirements.txt` организаторов
сохранён без изменений. Для полного окружения платформы зависимости нужно
установить из него и проверить совместимость отдельно.

Для экспериментов LightGBM дополнительно:
```powershell
.\.venv\Scripts\python.exe -m pip install lightgbm==4.6.0
```

## Подключение и первый запуск

Сначала можно выполнить `.\.venv\Scripts\python.exe check_api.py`.
Он запросит ключ скрыто и отправит короткий запрос; ключ не сохраняет и
переменные окружения для агента не задаёт.

Ключ вводится скрыто и не сохраняется в файле или истории команд:

Первую строку выполните отдельно, вставьте ключ в запрос ввода и нажмите Enter.
Только после этого выполняйте остальные строки в том же окне PowerShell.

```powershell
$secureKey = Read-Host 'API key' -AsSecureString
$env:OPENAI_API_KEY = [System.Net.NetworkCredential]::new('', $secureKey).Password
$env:OPENAI_BASE_URL = 'https://changellenge.up.railway.app/v1'
$env:OPENAI_MODEL = 'qwen/qwen3.8-27b'
.\.venv\Scripts\python.exe solution.py tasks/regression/task.md
```

Следующим запуском можно заменить путь на `tasks/classification/task.md`.
Ключ действует только в этом окне PowerShell и его дочерних процессах.
Файл `.env` автоматически не читается.

Для классификации:
```powershell
.\.venv\Scripts\python.exe solution.py tasks/classification/task.md
```

Не запускайте две копии агента одновременно в одной папке задачи: они могут
перезаписывать один submission.csv. API-ключ не отправляйте в чат или Git.
После закрытия PowerShell переменные нужно задать снова.

На Linux/macOS создайте окружение через `python3.12 -m venv .venv`, используйте
`.venv/bin/python` вместо Windows-пути. В Bash ключ можно задать скрыто:
```bash
read -rsp 'API key: ' OPENAI_API_KEY; echo
export OPENAI_API_KEY
export OPENAI_BASE_URL='https://changellenge.up.railway.app/v1'
export OPENAI_MODEL='qwen/qwen3.8-27b'
.venv/bin/python solution.py tasks/regression/task.md
```

По умолчанию в текущем коде: 60 шагов, 2 часа 45 минут на запуск, 20 минут на один эксперимент,
1800 секунд резерва на финальное обучение и минимум 10 успешных экспериментов
перед добровольным завершением Qwen. Лимиты времени/шагов имеют приоритет над
минимумом экспериментов. После 10 экспериментов агент может завершиться раньше.
Резерв ограничивается 30% общего бюджета. При временном таймауте/сбое соединения
или InternalServerError контроллер допускает до двух повторных попыток, если
достаточно времени. Ошибки ключа и лимита бюджета не повторяются.
Таймаут API не является строгим общим дедлайном; оставляйте запас до 3 часов.
Запуск расходует общий бюджет ключа. Скрипт не считает стоимость запросов.

Более длительный запуск после проверки короткого:
```powershell
.\.venv\Scripts\python.exe solution.py tasks/classification/task.md --time-budget 9900 --final-reserve 1800 --step-timeout 1200 --max-steps 60 --min-experiments 6
```

Для быстрого smoke-запуска задавайте старые лимиты явно:
```powershell
.\.venv\Scripts\python.exe solution.py tasks/regression/task.md --time-budget 1800 --final-reserve 450 --step-timeout 600 --max-steps 20 --min-experiments 4
```
Увеличение времени и числа шагов увеличивает потенциальный расход общего API-бюджета,
но не гарантирует улучшения. Встроенного денежного ограничителя пока нет.
LightGBM теперь принимает num_leaves (до 255 с учётом depth) и min_child_samples.

Сначала автоматически сохраняются предсказания лучшей модели, обученной на
обучающей части. В конце контроллер переобучает её на полном train с теми же
параметрами. Если переобучение прервано, ранний CSV остаётся доступен.
Сравнение выполняется на неизменном holdout; повторное использование одного
holdout для многих гипотез может привести к подгонке под него.
По умолчанию early_stopping_rounds=50: выбирается число деревьев по метрике
валидации (Macro F1 считается без весов). При полном переобучении используется
выбранное число деревьев, без повторного доступа к валидационным ответам.
Значение 0 отключает early stopping. Начинайте с небольших моделей.
Срок выполнения ограничен процессом, потоки обучения — 8.

## Генерация признаков и ансамбли

Qwen может передавать в train_model аргумент feature_code с функцией
`transform(X)`, возвращающей DataFrame с теми же индексами строк. Доступны np/pd
без импорта. Поддерживаются построчные отношения, взаимодействия, преобразования
и удаление признаков. Функция получает только признаки; применяется раздельно
к train/validation/test. Агрегаты, обучаемые кодировки и отбор по target в этом
интерфейсе не поддерживаются. Проверяются форма, индекс, схема и независимость
первых строк от обработки остального батча. Это базовые проверки, не доказательство
отсутствия любой утечки. AST-фильтр не является песочницей; исполняется локальный код.

blend_models принимает 2–3 ID экспериментов и необязательные положительные веса.
Для регрессии усредняются прогнозы, для классификации — вероятности в одном
порядке классов. Ансамбль сравнивается на том же holdout и сохраняется только
если лучше. При финальном обучении переобучаются все его участники; учитывайте
необходимый резерв времени. Нельзя подбирать много весов под один holdout.

История текущего запуска передаётся Qwen в каждом запросе. Старые журналы и
ручные эксперименты автоматически не загружаются. С --resume подаётся компактная
история выбранного запуска. Сравнение метрик внутри одного
запуска использует фиксированное разбиение; сменить его в середине нельзя.

`smoke_research_v2.py` проверяет новые возможности на публичной регрессии без API:
создаёт отдельную папку в work/, проверяет early stopping, удаление Year_Factor
и ансамбли. Итог — outputs/research_v2_smoke.json. Исходные CSV и предыдущие
submission/ZIP не заменяются. Этот скрипт не входит в архив платформы.

Результат: `submission.csv` рядом с `task.md`. В `agent_runs/` сохраняются
код шагов, stdout/stderr и история сообщений. Предыдущий submission переносится
в каталог текущего запуска, чтобы не принять старый результат за новый.

Дополнительно в каждом запуске:
- `events.jsonl`: параметры и результаты вызовов инструментов, включая ошибки;
- `research/state.json`: успешные эксперименты, метрики и выбранный победитель;
- `research/split.npz`: фиксированные индексы train/validation;
- `research/model_*.joblib`: модели экспериментов;
- `research/final_model.joblib`: модель после полного переобучения (если успешно).

Без --resume запуск начинает новое исследование; продолжение описано ниже.
Модель в joblib теперь хранится в словаре вместе с параметрами кодирования категорий.
Безопасно загружать только собственные доверенные joblib-файлы.

Генерируемый код исполняется с правами вашего пользователя. Отдельный процесс
и удаление ключей из его окружения не являются песочницей. Для изоляции
следующий этап — запуск в контейнере с доступом только к каталогу задачи.

Пути в оригинальных task.md могут отличаться от вашей раскладки: агенту
дополнительно передаются найденные реальные пути. Исходные условия не изменены.

Для платформы в корне ZIP нужны solution.py, research.py, xgb_backend.py,
diagnostics.py и исходный requirements.txt. Используйте сборщик.
Данные, локальное окружение и логи в ZIP не включайте. Полный запуск и
соответствие ограничениям платформы нужно проверить до отправки.

## Сборка и первая отправка

После проверки обеих задач из корня проекта:
```powershell
.\.venv\Scripts\python.exe -m unittest -v
.\.venv\Scripts\python.exe build_submission.py
```

Загрузите `outputs/automl_submission.zip` в форму решения трека AutoML.
Сборщик проверяет состав ZIP, целостность и соответствие файлов исходникам.
Внутри пять файлов в корне: `solution.py`, `research.py`, `xgb_backend.py`, `diagnostics.py`, `requirements.txt`.
Весь каталог проекта архивировать нельзя: там данные, модели и окружение.
После изменения кода пересоберите архив; ранее созданный ZIP сам не обновляется.

Платформа запускает `python3 solution.py task.md` и подставляет переменные API.
Предсказания и модели, полученные локально, не отправляются. На платформе агент
проводит новое исследование, поэтому результаты могут отличаться.
Сохранённая первая версия ZIP использует 30 минут, 20 шагов, резерв 450 секунд.
После пересборки в ZIP попадут новые лимиты из текущего исходного кода.
Локальные флаги командной строки в ZIP не сохраняются.
Полная установка requirements в Linux/Docker пока отдельно не проверена.

По инструкции организаторов: ZIP до 100 МБ, до 3 часов на задачу, 8 CPU,
32 ГБ RAM, до 3 сабмитов команды в день. Согласовывайте отправки внутри команды.

Проверенные локальные результаты на 21.10.2026:
| Задача | Лучшая модель | Валидация |
|---|---|---|
| Регрессия | LightGBM | RMSE 42.90935, случайное разбиение |
| Классификация | CatBoost, SqrtBalanced | Macro F1 0.63660 |

Это не оценки платформы и не гарантированный результат следующего запуска.

## Контролируемое сравнение LightGBM

`experiment_leaves.py` воспроизводит исходный эксперимент регрессии из локального
запуска `20261021_220854_212189`, перебирает число листьев и min_child_samples,
затем проверяет финалистов на переходах периодов 1–4 → 5 и 1–3 → 4.
Для запуска нужны исходные CSV и state.json/split.npz этого запуска (их нет в Git).
Скрипт предназначен для локального исследования, не включается в ZIP и не
используется агентом на скрытых задачах. Новые параметры доступны агенту универсально.

```powershell
.\.venv\Scripts\python.exe experiment_leaves.py
```

Результаты: `outputs/lightgbm_leaves_results.json` и `outputs/lightgbm_leaves_report.md`.
API не вызывается. Существующие submission.csv, модели и ZIP не заменяются.

Для сравнения CatBoost/LightGBM на одинаковых временных разбиениях:
```powershell
.\.venv\Scripts\python.exe experiment_temporal.py
```
Скрипт использует публичную регрессию: обучение на периодах 1–4, проверка на 5;
два лучших варианта каждого алгоритма затем проверяются на переходе 1–3 → 4.
Перебираются 200/600 деревьев и L2 3/10, добавлены два контрольных LightGBM
из предыдущего исследования. Признаки и learning_rate=0.05 фиксированы.
Локальный исследовательский скрипт не включается в ZIP; нужны CSV из tasks/regression.
Результаты сохраняются по мере выполнения в outputs/temporal_results.json,
в конце создаётся outputs/temporal_report.md. Валидационные предсказания также
сохраняются отдельно, без изменения submission.csv. Qwen и API не используются.

## Git: что отправлять

В Git нужны исходники, тесты, README, requirements и .gitignore.
Данные, модели, архивы, виртуальные окружения, ключи и логи исключены правилами
`.gitignore`. Небольшие итоговые метрики удобно записывать в README или отдельный
Markdown-отчёт вместо загрузки моделей и полных журналов.

Перед коммитом проверьте:
```powershell
git status --short
git diff --cached --stat
git ls-files
```

`.gitignore` не действует на уже отслеживаемые файлы. Если ранее добавили,
например, папку tasks, уберите только её из индекса через
`git rm -r --cached -- tasks` и закоммитьте изменение. Локальные файлы останутся.
Это не удаляет большие файлы из старых коммитов. Если ключ уже попал в историю,
его необходимо отозвать/заменить; одного удаления файла недостаточно.

## Частые ситуации

- `No suitable Python runtime found`: установите 3.12 и заново откройте терминал.
- `ModuleNotFoundError`: устанавливайте пакет через Python именно из `.venv`.
- Не задан API-ключ: задайте переменные в том же терминале, где запускаете агента.
- `Budget has been exceeded`: общий лимит ключа исчерпан; по инструкции сброс в 03:00 МСК.
- Ошибка/таймаут API: исследование прекращается; если есть успешный эксперимент,
  контроллер пытается выполнить финальное обучение и сохранить результат.
- Таймаут одного эксперимента: его процесс останавливается, агент получает ошибку;
  результаты предыдущих успешных экспериментов остаются.
- CSV прошёл проверку: подтверждён формат, а не качество на скрытом тесте.

## Продолжение исследования и второй агент

```powershell
.\.venv\Scripts\python.exe solution.py tasks/regression/task.md --resume tasks/regression/agent_runs/ИМЯ_ЗАПУСКА
```

Продолжение сохраняет разбиение, модели и результаты выбранного запуска. Старый
диалог архивируется, исследователь получает краткую память: все записанные
параметры/метрики/гипотезы, код признаков победителей и последние ошибки.
Полная предыдущая переписка автоматически не пересылается. Старые шаги не
перезаписываются, номера новых артефактов продолжаются. Разбиение заново не создаётся.
Минимум экспериментов относится к НОВЫМ экспериментам текущего продолжения.
Бюджет времени и шагов тоже отсчитывается заново для каждого запуска/продолжения.

manifest.json содержит SHA256 четырёх CSV, task.md, research.py и xgb_backend.py. При изменении
любого из них продолжение запрещается; нужно начать новое исследование.
Модели должны оставаться по сохранённым путям: перенос запуска между ПК пока
не поддержан. Можно менять контроллер solution.py и его инструкции.

Старые запуски, созданные до механизма контрольных сумм, требуют однократного
флага `--trust-legacy-run`. Он означает ручное подтверждение неизменности данных
и кода обучения: доказать их прежнее состояние программа не может.
Пример для нашего старого запуска (не выполнять одновременно с другим агентом):

```powershell
.\.venv\Scripts\python.exe solution.py tasks/regression/task.md --resume tasks/regression/agent_runs/20261022_013826_788168 --trust-legacy-run --time-budget 3600 --final-reserve 900 --max-steps 30 --min-experiments 5
```

После первого принятия сохраняется manifest, дальше флаг не нужен.
Не используйте его, если после прошлого запуска менялись данные или research.py.

Проверяющий включён по умолчанию. Это отдельный запрос к той же Qwen с отдельными
инструкциями, без инструментов выполнения кода. Он читает условие, журнал и код
лучших кандидатов, предлагает проверки. solution.py передаёт его замечания
исследователю. Замечания не заменяют метрики и сами могут быть ошибочными.
Вызов — при продолжении существующего исследования и каждые 6 новых записей
журнала (включая ансамбли). Частота: --review-every 6; отключение: --no-reviewer.
Нет фоновых процессов или параллельного обучения; оба агента работают последовательно.
Проверяющий получает краткую выборку лучших и последних опытов и код компонентов
победителя. Полная история остаётся у исследователя и на диске. Первая попытка
запрашивает reasoning_effort=none; если шлюз не поддерживает параметр, запасная
попытка использует стандартные настройки провайдера. Поддержку шлюза нужно проверить
реальным запросом; успешные локальные тесты её не подтверждают.
Лимит ответа проверяющего — 8000 токенов, включая рассуждение. Пустой или
оборванный ответ и ошибка API вызывают одну повторную попытку с лимитом 12000,
если остаётся время. Обе попытки используют общий бюджет времени проверки
(до 180 секунд, ограниченный остатком исследования). При неудаче выводится
Reviewer unavailable; ложное заключение об отсутствии замечаний не создаётся.
После двух неудачных попыток проверяющий отключается до следующего запуска,
чтобы не расходовать остаток времени на повторяющиеся сбои.

Новые файлы в папке запуска:
- memory.json — краткая история экспериментов;
- reviews.jsonl — запросы и заключения проверяющего, статус каждой попытки, finish_reason и расход токенов;
- usage.jsonl — токены исследователя и проверяющего, если API вернул usage;
- conversation_before_*.json — архив диалога перед продолжением;
- manifest.json — контрольные суммы входов и кода обучения.

usage — статистика токенов, не счёт в рублях; стоимость шлюза не рассчитывается.
Проверяющий расходует тот же бюджет ключа. Результаты ручных скриптов за пределами
журнала экспериментов не превращаются автоматически в подтверждённые наблюдения.

В папке задачи создаётся .agent.lock с PID, запрещающий одновременные запуски.
После аварийного завершения он может остаться: перед ручным удалением убедитесь,
что старый процесс действительно остановлен. При обычном завершении он удаляется.

На платформе запуск без --resume начинает исследование с нуля; переносится код
агента и его инструменты, а не локальные модели или датасеты. Теперь в ZIP также
входит diagnostics.py; сборщик учитывает его автоматически.

Дополнительные инструменты Qwen:
- read_experiment — полная запись опыта, код признаков и доступные метрики классов;
- inspect_categories — категории, неизвестные значения test и коллизии усечения строк;
- validate_experiment — дополнительная временная проверка сохранённой модели или
  ансамбля с фиксированными числом деревьев и весами. Не меняет основной score,
  сохранённые модели и submission.csv. Сейчас поддерживает числовую колонку времени;
  для классификации без времени используйте основное стратифицированное разбиение.

План для следующего API-запуска передаётся через --instructions experiment_plan.md.
Он добавляется отдельным сообщением Qwen и сохраняется в папке запуска.
Новые инструменты вынесены отдельно: research.py не менялся в этом обновлении,
поэтому продолжение существующего исследования с теми же CSV остаётся доступным.

Снимок завершённого запуска (модели, журнал, прогнозы и исходники):
`python save_checkpoint.py tasks/regression/agent_runs/20261022_013826_788168`.
Это локальный архив для восстановления, не ZIP для платформы. Датасеты и ключи
в него не включаются; нужны прежние CSV. При восстановлении абсолютные пути моделей
требуют исходного расположения проекта или отдельной адаптации путей.

Отдельная проверка ревьюера через API, без обучения:
`python check_reviewer.py tasks/regression/agent_runs/20261022_013826_788168`.

### XGBoost

train_model принимает algorithm="xgboost" для классификации и регрессии.
Используется XGBoost 2.1.4 из исходного requirements.txt, CPU hist, 8 потоков,
seed=42. Категории обучаются на тренировочной части, неизвестные категории
становятся пропусками. Строковые метки классов сохраняются; вероятности совместимы
с ансамблями CatBoost/LightGBM. Early stopping выбирает число деревьев по метрике
задачи: Macro F1/Accuracy максимизируются, RMSE/MAE минимизируются.

Параметры: iterations, depth, learning_rate, l2_leaf_reg, min_child_weight,
subsample, colsample_bytree, reg_alpha, gamma. Для классификации доступны
auto_class_weights="Balanced"/"SqrtBalanced"; веса вычисляются на train и
нормируются до среднего 1. Валидационная метрика считается без весов.
Не передавайте num_leaves/min_child_samples/random_strength для XGBoost.

Старые запуски продолжаются: прежний research.py и данные должны совпадать
по SHA256, а в истории могут быть только CatBoost/LightGBM/ансамбли. При первом
продолжении добавляется SHA256 нового backend, прежний manifest сохраняется как
manifest_before_xgboost.json. После этого изменение backend также блокирует resume.

План для классификации: --instructions classification_xgboost_plan.md.
Настоящий поиск моделей выполняется Qwen через API; локальные тесты нового backend
используют только небольшие синтетические данные и не измеряют качество на задачах.
Справочник API: https://xgboost.readthedocs.io/en/release_2.1.0/python/python_api.html
# Анализ ошибок сохранённых моделей

LightGBM дополнительно принимает `subsample`, `subsample_freq`, `colsample_bytree`,
`reg_alpha`, `min_split_gain`. Выборка строк включается только парой
`subsample < 1` и `subsample_freq >= 1` (например 0.8 и 1). Доля признаков задаётся
`colsample_bytree` независимо. Доли должны быть в (0, 1], регуляризация — конечной
и неотрицательной. Настройки сохраняются в рецепте и используются при финальном
обучении. Старые рецепты без новых параметров сохраняют прежнее поведение.
Совместимость старой истории разрешена только для конкретной проверенной пары
хэшей кода при неизменных данных и остальных файлах манифеста; старый манифест
копируется в `manifest_before_upgrade_<время>.json`. Произвольные изменения кода
или данных по-прежнему блокируют продолжение.

План проверки новых параметров: `lightgbm_sampling_plan.md`. Команда:

```powershell
.\.venv\Scripts\python.exe solution.py tasks/regression/task.md --resume tasks/regression/agent_runs/20261022_013826_788168 --instructions lightgbm_sampling_plan.md --time-budget 7200 --final-reserve 1200 --max-steps 60 --min-experiments 8 --review-every 12 --analyst
```

Qwen доступны `analyze_errors(experiment_id, group_columns, min_group_size)` и
`compare_errors(experiment_ids)` для пары разных опытов. Первый инструмент показывает
precision/recall/F1 классов, частые перепутанные классы и качество по уверенности;
для регрессии — MAE, RMSE, смещение и квантили абсолютных ошибок. Можно указать
до трёх исходных признаков для группового анализа. Границы числовых групп вычисляются
только на обучающей части. Вывод ограничен 15 крупнейшими группами каждого признака.
Второй инструмент сравнивает ошибки на одних и тех же строках валидации.

Инструменты не обучают модели и не меняют победителя или сабмит. Для ансамбля без
кэша используются сохранённые модели валидации, а не модель, дообученная на всём train.
Полные отчёты: `tasks/<задача>/agent_runs/<запуск>/error_analysis/`.
Индекс сводок: `error_analysis.json`; последние три сводки получают исследователь
при продолжении запуска и проверяющий при очередном вызове. Внутри текущего запуска
исследователь видит ответы инструментов непосредственно в диалоге.
Малые группы и многократный подбор на одном holdout требуют осторожной интерпретации.

Для продолжения классификации после опыта 28:

```powershell
.\.venv\Scripts\python.exe solution.py tasks/classification/task.md --resume tasks/classification/agent_runs/20261022_143503_454151 --instructions classification_error_analysis_plan.md --time-budget 7200 --final-reserve 1200 --max-steps 60 --min-experiments 8 --review-every 12
```

Для третьей роли добавьте `--analyst` к команде. Проверяющий и аналитик ошибок
работают в двух фоновых потоках через тот же Qwen API, пока исследователь продолжает
эксперименты. Возможны три одновременных API-запроса; фактическая параллельность
зависит от ограничений провайдера. Аналитик выключен по умолчанию.
Перед запуском консультантов контроллер получает свежий analyze_errors для победителя.
Каждый консультант получает неизменяемый снимок истории; готовые советы передаются
исследователю между шагами с номером снимка. Только исследователь запускает обучение.
Советы аналитика сохраняются в `analyst_reviews.jsonl`, проверяющего — в `reviews.jsonl`.
Частота обоих задаётся `--review-every`; при продолжении первая проверка запускается
сразу, если осталось более 200 секунд. Повторный запрос роли не запускается, пока
предыдущий не завершён. После двух неудачных попыток отключается только сбойная роль.
При завершении контроллер дожидается ограниченных по времени запросов консультантов;
это может занять часть резерва финального обучения. Дополнительные роли расходуют API-токены.
API настраивается в текущем терминале как обычно. Для обновлённого кода нужен новый процесс.
